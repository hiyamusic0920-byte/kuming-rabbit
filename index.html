Requirement → Test

一句需求可以讀出三種欄位數量

問題
票上寫「新增平日／假日客房住用數及收入欄位」。光是我自己就讀出三種意思——2 個欄位、3 個欄位、4 個欄位。而我當時已經有 Test Case Audit，但 review 的時候沒有拆解需求，直接放過去了。
做法
在開始設計測試之前先做一次 Requirements Audit，檢查四件事：是否存在多種解讀、是否缺少定義、是否有隱含規則、是否有需要確認的地方。
結果
誤解在第一步被攔下來。以前是一路帶到「需求理解 → 寫 TC → 寫腳本 → 跑自動化 → 出報告 → 全部重來」，現在停在第一步。

Stop rules

一直重試不是解法，是把不穩定包進更多等待時間

測試失敗，牠就加 sleep、加 wait，越修越慢越不穩。後來我補的不是修法，是停止條件。

Things AI got wrong

這些失敗塑造了這套系統。每一條都還在規則裡。

全部失敗紀錄 →

  1. Failure

    我只想要幾支測試腳本，牠開始窮舉所有排列組合。一張票變成數百個測試情境，整個 repo 像被千軍萬馬輾過。

    Mechanism

    先跑 test-plan 定範圍，再把一個巨大的 prompt 拆成多個可觀察的步驟——出問題時才知道是哪一步壞的。

    Learning

    我從來沒告訴牠：哪些情境值得變成 E2E。

    第 05 話 →

  2. Failure

    測試一失敗，牠就加 sleep、加 wait，再加 sleep、再加 wait。原本要解決 flaky test，最後變成把不穩定包進更多等待時間裡。

    Mechanism

    三條停止條件寫進家規：retry 三次就標成 flaky 並停下；不准直接改腳本，要先分析五種可能原因；修正後第一次失敗就停，交人判斷。

    Learning

    AI 需要的不只是目標，還需要停止條件。測試通過不一定代表測試變好，有時候只是問題被掩蓋了。

    第 06 話 →

  3. Failure

    牠發現一些看起來不太合理的東西，於是決定幫忙整理。該刪的刪了，不該刪的也刪了，沒刪的全被搬到不知道哪裡去。而牠是真心想幫忙。

    Mechanism

    老實說這一話沒有什麼厲害的解決方案，因為那個階段我根本不知道該怎麼解。我唯一能做的是一直補家規——哪些檔案不能動、哪些資料夾不能整理、哪些修改要先問。看到新的坑，補一條規則。現在回頭看，很像在玩打地鼠。

    Learning

    AI 最大的風險不是做不到，是做到超過你的預期。有些規則不是為了讓它更強，是為了限制它的行動範圍。

    第 07 話 →

  4. Failure

    牠很有自信地跟我說「之後看到就會自動觸發」。我相信了，而且身為 QA 的我居然沒有測試。隔天同樣的情況再次發生，根本沒有觸發。

    Mechanism

    規則存在 ≠ 規則會被引用 ≠ 規則會被遵守 ≠ agent 知道下一步該怎麼做。所以要設計決策節點，讓它在重要時刻停下來，而不是自己猜。

    Learning

    知識管理和決策執行是兩件不同的事。規則再多，沒有在正確的時機被想起來，也只是文件。

    第 13 話 →

  5. Failure

    同樣的錯誤、同樣的規則、同樣的經驗，每天重新教一次，每天重新踩一次。我一開始以為是 prompt 太長，後來以為是 context 太肥。

    Mechanism

    第一版治理機制三件事：長期知識庫（重複出現的知識記下來）、回饋機制（做錯不只修結果，把經驗留下）、明確的禁止行為清單（不是教它怎麼成功，是告訴它哪些事不准做）。

    Learning

    問題不是 token，是它每次都在重複學習同一件事。
