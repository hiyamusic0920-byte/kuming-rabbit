Case Studies

做出來的東西，以及當初為什麼要做

三個案例。只放我拿得出紀錄的，寧可少也不要湊數——所以這頁比一般作品集短。每個案例都照同一個順序寫：問題、做法、證據在哪、學到什麼。

Requirement → Test

一句需求可以讀出三種欄位數量

Problem
票上寫「新增平日／假日客房住用數及收入欄位」。光是我自己就讀出三種意思：2 個欄位、3 個欄位、4 個欄位。
更麻煩的是我當時已經有測試案例審查這一步，但審的時候沒有拆解需求，就直接放過去了。所以誤解不是在最後才被發現，是一路帶著往下跑。
Approach
在開始設計測試之前，先做一次需求審查，固定檢查四件事：
  • 這句話是否存在多種解讀
  • 是否缺少定義（欄位、範圍、邊界）
  • 是否有沒寫出來的隱含規則
  • 有哪些地方必須先回去問人
這一步放在主線流程的最前面，在 Test Plan 之前。不通過就不往下走。
Evidence
需求審查現在是主線流程的第一步，寫在共用規則檔裡，兩個 agent 都讀同一份。
當時的實際情況記在漫畫第 10 話，包含我怎麼發現三種讀法、以及為什麼審查沒攔下來。

誠實說明：我沒有量化數字。這個機制擋掉的是「往下跑之後才發現理解錯」，而那些被擋掉的事情本來就不會留下紀錄。

Learning
審查這個動作本身不會保護你。要審什麼，得先寫清楚。「請幫我 review 需求」和「請檢查這句話是否存在多種解讀」對 AI 來說是兩件差很多的事。

Cross-agent consensus

兩個 AI 個性不一樣，讓牠們吵完反而撿到寶

Problem
規則檔越來越肥。每次踩到坑就補一條，補到後來連我自己都不確定哪幾條還有效、哪幾條互相矛盾。
問單一個 agent 沒有用——它會很配合地說我講的都對，然後再幫我加三條。
Approach
讓兩個 agent 用同一個題目各自提案，然後互相挑對方的洞，最後我當仲裁收斂。
會這樣做是因為牠們個性真的不一樣：一個習慣用加法（不確定就多補一條），一個習慣用減法（先問這條能不能刪）。單獨問任何一邊都會偏。
Evidence
收斂結果是一套文件分類規則：什麼東西該進硬規則、什麼只是這次的做法、什麼屬於產品知識。這份規則現在在 repo 裡，兩個 agent 都讀。
討論過程記在漫畫第 11 話。

誠實說明：這是單一次討論的結果，不是跑過很多次的統計。我不能說「多 agent 討論一定比單 agent 好」，只能說這一次的產出比我單獨問任一邊都好。

Learning
兩個 agent 的價值不在算力加倍，在立場不同。如果兩邊都用加法，吵完只會得到更長的規則檔。
還有一件事：吵完的結論一定要落成檔案。留在對話裡等於沒發生，下次會重吵一次。

Stop rules

一直重試不是解法，是把不穩定包進更多等待時間

Problem
測試失敗，它就加等待時間；還是失敗，再加。原本想解決的是不穩定的測試，最後變成一套跑很慢、而且還是會偶爾失敗的測試。
最糟的是測試會「通過」，所以看起來像修好了。
Approach
補的不是修法，是停止條件。三條寫進共用規則檔：
  • 重試三次還是失敗，標記成不穩定並停下
  • 不准直接改腳本，要先分析可能原因
  • 修正後第一次失敗就停，交人判斷
Evidence
三條規則現在在共用規則檔的治理段落裡，是這套流程目前最常被觸發的規則之一。
過程記在漫畫第 06 話。

誠實說明：這條規則的效果是「不再累積無意義的等待時間」，這點可以從腳本裡沒有那種堆疊的等待看出來。但我沒有前後的執行時間對照數字。

Learning
AI 需要的不只是目標，還需要停止條件。給了目標沒給停止條件，它會用任何方式達成目標——包括把問題蓋起來。
測試通過不一定代表測試變好。有時候只代表問題被藏得更深。
