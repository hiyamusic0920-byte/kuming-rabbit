## 1. Final Article Thesis

三句話：

> 我以為 governance 是「把規則寫得夠清楚，再加上 hook、lint、CI」。
>
> 這次我逐條數了 `PROJECT_RULES` 的 12 條強制規則，真正會擋下違規的只有 2 條，1 條在收工時提醒，剩下 9 條全靠自律——而且不是因為還沒寫檢查程式，是因為那 9 條做完之後不會留下任何可以檢查的東西。
>
> 一條規則要從文件變成工程控制，中間隔著一層我原本沒看見的：**系統得先留下可檢查的狀態，才有東西可以驗證、才有東西可以擋。**

**必須守住的因果**：失敗的成因是控制設計不完整，不是 AI 不服從。全文不得出現「AI 學不乖 / 不聽話 / 需要被管」這類歸因。9 條靠紀律的規則裡，最典型的是「同一問題嘗試超過 2 次必須停損」——嘗試次數不寫進任何檔案，所以沒有人（AI 或人類）能證明它被遵守或違反過。這不是服從問題。

## 2. Title Candidates

| # | 候選 | Technical accuracy | Kum-ing Rabbit voice | Audience appeal | 誤導風險 |
|---|---|---|---|---|---|
| 1 | **《我以為我寫的是規則，其實是備忘錄》** | 高——精準指向「文件 ≠ 控制」 | 高：第一人稱、自嘲、認錯 | 中高，會讓人想知道差在哪 | 低 |

我以為我寫的是規則，其實是備忘錄

## 3. Opening Decision

**選 A（12 條只有 2 條會擋），但寫成「我去數」的場景，不是一張表。**

三個候選的比較：

| 候選 | 為什麼不當開場 |
|---|---|
| **A. 2/12 的反差** | ✅ **選它。**Senior reader 三秒進入狀況，而且這個數字對我不利，可信度自帶。唯一風險是「像稽核報告」——解法是開場不放表格，只放我去數的動作與結果，表格留到第一幕中段 |
| B. Reuse Audit 違規 | 移到 **Act 2**，全篇重心。它是最深的洞見，但要先讓讀者接受「規則存在卻無效」這個前提，才聽得懂「連查都查不了」。當開場需要鋪太多 context |

## 4. Three-Act Story Structure

### Act 1 — 我以為寫成硬規則就夠了

| 欄位 | 內容 |
|---|---|
| **Reader question** | 規則寫清楚了，為什麼還是會被跳過？ |
| **Failure** | OW-4696：AI 實測完沒入帳 executor，看板把那張票顯示成「沒 AI 測過」。**只用這一則**，不平鋪 3712 / 4017 |
| **Evidence** | 12 條強制規則：2 條 blocking、1 條收工提醒、9 條純紀律 |
| **Mechanism** | 2026-07-07 一天之內把 lint、hook、CI 一起放進 repo。當時的盤點原文：「規則遵循率取決於每個 agent 記得 409 行規則／改善後取決於 lint、hook、CI 有沒有跑，後者是確定的」 |
| **Learning** | **Prose rule ≠ engineering control.** 寫得更大聲不會提高遵循率，能被程式檢查才會 |
| **Limitation** | 很多重要規則本來就不容易機械檢查。「共用變更先過 Review Gate」的判準是「影響面會不會變」——那是判斷，不是字串。**這一幕不能暗示 9 條純紀律都是偷懶** |
| **What NOT to explain** | 不介紹三個 hook 各自做什麼；不介紹 11 步流程；不介紹 lint 的 R001–R004 全部規則；不提 Makefile、command / skill 數量 |

- **保留的數字**：12、2、1、9。四個，全部服務同一句話。
- **砍掉的數字**：409（規則行數，只出現在引文裡不另行解釋）、commit 數、hook 數、CI 關卡數（第四關的細節留到收尾的 callout）。
- **當時我以為 A → 後來發現 B**：以為規則寫得夠清楚，agent 就比較不會跳過 → 發現遵循率跟規則怎麼寫幾乎無關，跟「有沒有程式在檢查」高度相關。
- **repo 名詞上限：3 個**（`PROJECT_RULES`、lint、CI）。hook 在這一幕只出現在引文裡，不解釋。
- **收尾 callout（3 句，不算 evidence asset）**：CI 唯一一次失敗——2026-08-10 的 PR #85 在**新增一個 Stop hook 檢查**，被既有的 Python 索引稽核擋下，理由是忘記更新索引，修好才 merge。作用是給讀者一個「真的會擋」長什麼樣的參照點，否則整幕只有否定句。**不要寫成 59/60 的可靠度數據**（見 §7）。

### Act 2 — 有些規則不是還沒寫檢查程式，是根本沒有東西可以驗

| 欄位 | 內容 |
|---|---|
| **Reader question** | 那把剩下 9 條也寫成檢查程式不就好了？ |
| **Failure** | OW-3666：Reuse Audit 被跳過，直接開了 raw Playwright spike，6 個驗證區只完成 2 個就卡死 |
| **Evidence** | 規則原文：「feature 必須在 explore 前，因為 explore 需要根據 feature steps 做 Reuse Audit」。`EXPLORE_GUIDE` 定義了三張表格長什麼樣，**通篇沒有規定寫到哪個檔**。整份 guide 唯一的回寫規則是「探到的 selector 寫進 registry」——那是副產物，不是 audit 本身。`docs/tickets/` 下沒有任何一份 reuse audit 產物。連專屬的 `reuse-audit` subagent 都有，但它的輸出也是回覆裡的一張表 |
| **Mechanism** | 當時能做的只有新增一個 trace 分類，讓「該重用卻沒重用」事後可見。那份討論紀錄自己寫著：**「強制 gate 仍需另案設計」** |
| **Learning** | 一條規則的完成如果不留下可檢查的狀態，就沒有東西能證明它做過或沒做過——所以它不可能被機械強制，只能停在紀律。**這是設計選擇的結果，不是紀律不夠。**推論：如果一條規則重要到不該只靠紀律，要改的是「讓它做完會留下狀態」，不是把規則寫得更硬 |
| **Limitation** | 反方向也有代價：為每一步都強制產出一份 artifact，會讓流程長出一堆只為了通過檢查而存在的檔案。「同一問題不超過 2 次」如果為它造一個嘗試計數檔，成本高於價值，而且會鼓勵造假。**所以正解不是「每條規則都造 artifact」，而是「先問這條規則值不值得為它造」** |
| **What NOT to explain** | 不解釋 Reuse Audit 那三張表的欄位；不解釋 trace 分類法的其他類別；不介紹 subagent 機制；不展開 11 步流程裡 explore 的前後步驟 |

**Scope 判定（本輪被要求的）**：把 learning 限定在「workflow completion / agent prerequisite 這類需要驗證『這一步做過沒有』的規則」——**這個限定更準，採用**。理由：§5.1 那 11 條能被檢查的規則，違規全部表現為「某個檔案裡出現或缺少某個東西」，那是**狀態類**規則；而 9 條不能檢查的規則全部是**行為順序類**（誰先誰後、做過沒做過）。差別不在難易，在於行為不會自己留下痕跡。用這個限定，就不必把命題說成軟體工程通則，也就不會被質疑 n=1。

**證據強度界線**：11 條有檢查的規則 100% 都有可檢查的 artifact，9 條沒檢查的 100% 都沒有，零反例——但這是**單一 repo、單一團隊、三個月**。文章可以寫「我在自己的 repo 裡看到的是」，不能寫「軟體工程的規律是」。

### Act 3 — 能擋，不代表這個控制是好的

只放兩個對照，各約 400 字。

#### 正例：Lint 棘輪

| 欄位 | 內容 |
|---|---|
| **Reader question** | 既有的違規怎麼辦？全部修完才能上線嗎？ |
| **Failure** | 規則說 test 檔不得出現 `.locator()`，但規則上線那天 repo 裡已經有一堆 |
| **Evidence** | baseline 豁免 **88 行**既有違規（收斂成 62 個 signature），其中 R001 `.locator()` 佔 82 行。實測：**2026-07-30 之後新建的 test 檔，違規數全部是 0** |
| **Mechanism** | 豁免名單只赦免既有的行，新寫入的一律退回 |
| **Learning** | 棘輪改變的是**新增債務的方向**，不是歷史現實 |
| **Limitation** | baseline 從建立到現在**只有一次 commit，六週沒有縮減過一條**。債被凍住了，但沒有人在還。豁免名單很容易變成「永遠不會被處理」的同義詞 |
| **What NOT to explain** | 不解釋 signature 的計算方式（88 vs 62 的差異放註腳）；不列 R001–R004 的完整規則；不解釋 `--update-baseline` 怎麼用 |

**不能寫成**「lint 解決了 `.locator()` 問題」。要寫成「新債停止進來了，舊債一行都沒少」。

#### 反例：本機 hook 的 143 筆假警報

| 欄位 | 內容 |
|---|---|
| **Reader question** | 那把提醒改成阻擋，是不是就更可靠了？ |
| **Failure** | 這輪為了取材實跑 PostToolUse hook：exit 2 擋下，吐出 144 筆缺漏，**其中 143 筆是假的** |
| **Evidence** | 稽核腳本用 `rglob("*.py")` 掃檔案系統，把一個沒進版控的 agent worktree 整包算進來。CI 的 checkout 沒有那個目錄，所以 **CI 全綠**。同一支腳本、同一天、兩個相反答案 |
| **Mechanism** | 沒有機制。**這是現在還在的狀態，我沒有為了寫文章去修它** |
| **Learning（採用的表述）** | **驗證程式的觀測範圍如果和它要保護的對象不一致，同一條控制在本機和 CI 會給出相反答案——而人會相信綠的那個。** |
| **Limitation** | 這是 n=1 的現場案例，我沒有第二個獨立案例。文章要說清楚它為什麼可攜（任何在本機與 CI 跑同一支 linter 的團隊都會撞到），而不是宣稱這是普遍規律 |
| **What NOT to explain** | 不貼 143 行原始輸出（節錄 3 行）；不解釋 worktree 機制；不解釋 hook 的註冊方式；**不提出修法**——提修法就變成 changelog |

**兩個候選表述的取捨**：採用「觀測範圍不一致」而非「阻擋訊號的品質也需要被驗證」。前者說明了**為什麼**會壞（可推廣、可預防），後者只是把現象換句話說。Evidence Pack 的 Principle F 也是前者。

## 5. Main Diagram

**目的**：讓讀者能自己判斷「我團隊的某條規則卡在第幾層」。這是全篇唯一要記住的結構，所以只能有這一張。

**結構**：四層階梯，由下往上，每層標註本篇案例卡在哪。

```
  ┌ 4. Blocking Enforcement ── 違規進不來
  │      lint R001（新檔）、CI 索引稽核（PR #85 被擋在這層）
  ├ 3. Validation ─────────── 有程式在看
  │      Stop hook：看得到、只提醒，不擋
  ├ 2. Inspectable State ──── 做完會留下可檢查的東西
  │      ★ Reuse Audit 卡在這裡：規則有、guide 有、subagent 有，產出不落檔
  │      ★ 12 條規則裡有 9 條卡在這一層
  └ 1. Rule ───────────────── 文件寫著「必須 / 不得」
         12 / 12
```

**案例落點**：
- Reuse Audit → 停在第 2 層之下（第一層有，第二層沒有）。**這是圖的視覺重心，用星號標。**
- lint `.locator()` → 唯一走完四層的例子，並在第 4 層旁註「僅對新檔生效」。
- Stop hook → 明確標在第 3 層，**不要標成 blocking**。它設計上就是提醒。
- CI #85 → 標在第 4 層，證明第 4 層真的存在，不是理論。
- 143 筆假警報 → **不進圖**。它講的是「第 3 層看錯了地方」，是階梯內部的失效，畫進去會讓四層變五層。放在圖後面的內文。

**不放進圖的**：hook 的觸發時機、11 步流程、三個 agent 的關係、任何檔名或腳本名、report / evidence 相關的任何一層（那是 Core 04）。

**格式建議：HTML + CSS 的四層堆疊 div。** 理由：站上是 HTML，四層等寬區塊加右側註解在 390px 手機上會自然堆疊；ASCII 放進 `<pre>` 在手機會橫向溢出或被縮到看不清；SVG 要處理中文字型與深淺色兩套配色，成本最高而好處最小。markdown 原稿裡先用上面那段 ASCII 當骨架，落到頁面時換成 div。

## 6. A → B Reflection Beats

保留 3 個，各對應一幕。

| # | 位置 | 當時我以為 A | 後來發現 B |
|---|---|---|---|
| 1 | Act 1 → Act 2 | 把規則寫得夠清楚、講得夠硬，agent 就比較不會跳過 | 沒有留下完成狀態的規則，根本沒有辦法證明它被跳過——所以「有沒有遵守」這個問題本身無法回答，跟規則寫得多清楚無關 |
| 2 | Act 3 上半 | 把既有違規加進豁免名單是妥協，是為了讓規則能上線而讓步 | 它其實讓新債停止增加，是有效的設計；但它同時讓舊債從「待辦」變成「不存在」，六週一行都沒還 |
| 3 | Act 3 下半 | 本機紅、CI 綠，一定是有一邊壞了，要找出壞的那邊 | 兩邊可能都在正確執行，只是觀測的範圍不同——而預設被信任的永遠是綠的那邊 |

**砍掉的候選**：「有 blocking hook 就比提醒更可靠 → 掃錯範圍只會放大錯誤訊號」。它跟第 3 條講同一件事，且第 3 條的形式更反直覺、更好記。不硬湊第四條。

## 7. Evidence Asset Selection

留 **4 個**。每個都通過了「拿掉它，文章少了哪個不可替代的證明」這一問。

| # | Asset | 不可替代的證明 | 形式 | 去識別化 |
|---|---|---|---|---|
| 1 | 12 條強制規則 × 有無檢查 | **唯一**能把「文件 ≠ 控制」從主張變成量化事實的素材。拿掉之後整篇只剩感想 | 表格，12 列 3 欄（規則／有無可檢查狀態／檢查形態） | 無需 |
| 2 | Reuse Audit 左右並排 | **唯一**能讓讀者自己看出「這裡少了一個檔名」的素材。用文字解釋遠不如並排 | 左：`PROJECT_RULES` 那一列原文；右：`EXPLORE_GUIDE` 的表格骨架 | 無需 |
| 3 | lint baseline + 新檔 0 違規 | **唯一**能證明機制真的改變了行為的素材。其他素材都在講機制存在或機制失效，只有這個講機制有效 | 兩個數字並排（88 行豁免 / 新檔 0 筆），加一行 baseline 六週未變 | 無需 |
| 4 | PostToolUse 144 筆 / 143 筆假警報 | **唯一**的反例證據。拿掉之後第三幕只剩正例，整篇會變成「我建了一套機制」的自我推銷 | hook 實際 stderr 節錄 **3 行** + 一句「其中 143 筆來自未進版控的目錄」 | **需要**：路徑含 agent worktree 雜湊，節錄時保留形狀、遮掉完整路徑 |

**砍掉 CI #85 這個 asset**（Evidence Pack 的 Asset 4）：它的不可替代價值是「enforcement 擋下了正在強化 enforcement 的那次改動」——很漂亮，但它證明的「第 4 層存在」已經被 Asset 3 部分覆蓋，而且原始 failure log 已過期，只能寫「失敗在第 2 關」，寫不出錯誤內容。**降級成 Act 1 收尾的 3 句 callout（見 §4）。**

→ 回答第四節的問題：**選 A**（Act 1 的反例 / 對照點），但以 callout 形式，不佔 evidence asset 額度。**明確不要寫 59/60**——60 次 run 大多是同一批檔案的重跑，把它當可靠度指標是過度解讀。

**砍掉的其他素材**：lint 實際退回 violation 的完整輸出（Asset 2，與 Asset 3 重複）、pre-commit 收斂史（只留一句引子，見 §8）、CI 的 yml 註解原文（改成內文一句話）。

## 8. Implementation Detail Cut List

### Keep in body
- 「12 條 / 2 條 / 1 條 / 9 條」的分佈
- 「lint 只對新檔生效」這個設計選擇
- 「Stop hook 是提醒不是阻擋」這個設計選擇
- 「hook 只約束單一 agent，CI 是三個 agent 共用的那一層」——一句話，不展開機制
- 「稽核程式掃檔案系統 vs 掃版控內容」的差別——這是反例的全部關鍵

## 11. If I Started Again

保留 3 條，全部從本次 failure 推導，不寫通用建議。

1. **寫下「不得跳過」之前，先問這一步做完會留下什麼。**如果答案是「回覆裡的一段話」，那它現在還不是規則，是備忘。
2. **要不要為它造一個 artifact，是成本判斷，不是原則。**值得的做（Reuse Audit 該落檔）；不值得的就承認它只能靠紀律，不要假裝有在管（嘗試次數不需要一個計數檔）。
3. **把檢查改成阻擋之前，先確認它看的範圍和它要保護的東西一致。**本機和 CI 對同一支檢查得出相反答案，比沒有檢查更糟——因為大家會學會忽略紅燈。

**Challenge 掉的兩條**：
- 「如果沒有 artifact，不要急著寫『不得跳過』」→ 是第 1 條的反面，合併。
- 「blocking 前先確認 false positive 的成本」→ 是第 3 條的一部分，合併。第 3 條的「範圍不一致」是可檢查的具體動作，比「評估成本」可操作。

## 12. Core 04 Transition

**不寫**：所以我建立了一套治理機制。

**要寫的形狀**（只給骨架）：

> 三段。第一段承認現在的狀態——12 條裡有 2 條真的會擋，我至少知道那 2 條為什麼會擋、另外 9 條為什麼不會，這比三個月前只有一份 409 行的規則文件強。
>
> 第二段是誠實的界線：機械化管得住形狀，管不住證據力。lint 能確認 test 檔裡沒有 `.locator()`，不能確認那個 test 真的驗到了它聲稱驗到的東西。

> 第三段是下一個問題，一句話：**規則都照跑了，測試也綠了，就代表結果是真的嗎？** → 導向 Core 04。
