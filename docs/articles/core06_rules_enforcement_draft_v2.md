# 我以為我寫的是規則，其實是備忘錄

> 12 條硬規則，真正會擋下違規的只有 2 條

## 我去數了一遍

我的測試 repo 裡有一份規則文件。

四百多行，我自己寫的，開頭第一句就要求所有 agent 動工前先讀完。三個 agent 都被要求讀：Claude、Codex、Gemini。

裡面有一張表，標題叫「強制規則」。

「強制」兩個字是我自己打上去的。

那張表寫好三個月後，我做了一件之前沒做過的事：我沒有去問「有沒有人違規」，而是逐條去數——**這 12 條，如果現在有人違反，會發生什麼事？**

會被擋下來的：**2 條。**

會在收工時被念一句的：**1 條。**

剩下 **9 條**，什麼都不會發生。

我原本以為這 9 條只是還沒排到，等我有空把檢查程式寫完就好。

後來發現不是。

## 規則寫在那裡，但沒有人在看

先講最單純的那種失敗。

流程規定，AI 測完一張票，要把「這張票是誰測的」寫進一份帳本。有一張票，AI 從頭到尾測完、報告也出了，帳本沒寫——於是看板上那張票顯示成「沒有 AI 測過」。

這種失敗好處理，因為條件很乾淨：有新的報告檔案、卻沒有對應的帳本記錄，兩個檔案一比就知道。

我在七月初一次把能比的都補上。同一天，靜態檢查、編輯期的檢查點、還有 CI 一起進 repo。

那天的盤點紀錄裡有一句，現在回頭看是最有用的一句：

> 規則遵循率，原本取決於每個 agent 有沒有記得那四百多行；改完之後取決於檢查程式有沒有跑。後者是確定的。

差別不在規則寫得多清楚。

在於有沒有東西可以拿來比對。

**【插入：12 條強制規則 × 檢查形態對照表】**

| 規則（`PROJECT_RULES` 強制規則表） | 做完會留下可檢查的東西嗎 | 現在會怎樣 |
| --- | --- | --- |
| test 檔不能出現 `.locator()` | 有：檔案內容 | **擋下** |
| feature 的 Background 不寫登入 | 有：檔案內容 | **擋下** |
| POM 寫完後必須回補頁面知識 | 有：這次改了哪些檔 | 收工時提醒 |
| test plan 必須在 test case 前 | 沒有 | 什麼都不會發生 |
| feature 必須在 explore 前 | 沒有 | 什麼都不會發生 |
| explore 前必須先讀既有的 POM 與頁面知識 | 沒有 | 什麼都不會發生 |
| 只有找不到 selector 才開瀏覽器工具 | 沒有 | 什麼都不會發生 |
| 開瀏覽器工具必須帶登入狀態 | 沒有 | 什麼都不會發生 |
| POM 必須在測試步驟前 | 沒有 | 什麼都不會發生 |
| 切換旅館必須走統一的方法 | 沒有 | 什麼都不會發生 |
| 同一個問題試超過 2 次必須停損 | 沒有 | 什麼都不會發生 |
| 會影響別票的改動要先有人看過 | 沒有 | 什麼都不會發生 |

這張表只涵蓋那份文件裡的「強制規則」12 條。repo 裡還有幾類檢查是會擋的——報告的資料格式、報告檔案的落點、程式索引的完整性——它們不在這張表裡[^1]。所以別把「只有 2 條」讀成「整個 repo 只有兩個守門的」。

我要說的是更窄、也更難看的一件事：**我親手標上「強制」的那 12 條，四分之三強制不了。**

> **短註：真的會擋是什麼感覺**
> 有一次 CI 擋下我自己的變更，而那個變更正在**新增一個檢查**。它被既有的程式索引稽核攔住，理由是我忘記同步索引，修好才進得去。
> 「擋下來」就是這個樣子——不看你在做好事還是壞事，條件不滿足就是不行。

## 有些規則不是還沒寫檢查程式，是根本沒有東西可以驗

現在講那 9 條。

我原本的計畫是照上面那套做法一路補完。挑一條最重要的先辦——那條叫 Reuse Audit。

規則長這樣：**探索頁面之前，必須先盤點現有的 Page Object 和頁面知識，確認哪些步驟已經有人寫過了。**

理由很硬：上一張票摸清楚的頁面，下一張票不該重新摸一次，否則不只浪費時間，還會寫出兩份互相矛盾的 selector。

配套也齊全。流程文件有專門一段規定產出格式，要三張表格。我甚至為它寫了一個專用的 subagent，唯讀，只做這件事。

然後它被跳過了。

有一張票，AI 沒有盤點，直接開了一支 raw Playwright 腳本自己摸。六個要驗的區塊，做到第二個就卡死。

我當時的反應是「補一個檢查把它擋住」。

打開流程文件想確認要檢查什麼，才看到問題。

**【插入：左右並排——規則原文 vs 產出規定】**

左邊，硬規則那一列：

> feature 必須在 explore 前 —— explore 需要根據 feature steps 做 Reuse Audit

右邊，流程文件的「輸出格式」段：

> （三張 markdown 表格的欄位定義）

右邊沒有檔名。

整段規定了那三張表要長什麼樣、要有哪些欄位、每一列要標信心水準——**沒有規定寫到哪裡去。**

所以它的產出是什麼？是對話裡的一段文字。

整份流程文件只有一條回寫規則：探索過程中發現的 selector 要寫進頁面知識庫。那是副產物，不是盤點本身。我去 ticket 目錄找，一份盤點產物都沒有。那個專用 subagent 也一樣，輸出是回覆裡的一張表。

於是我要加的那個檢查，沒有可以檢查的對象。

不是難寫。是**沒有東西可寫**。

我當時能做到的只有一件事：新增一個事後標記，讓「該重用卻沒重用」在紀錄裡看得見。那份設計紀錄的最後一句是我自己寫的：

> 這只能讓失敗可見，不能強制。強制的機制仍需另案設計。

到今天還是沒案。

### 為什麼卡得這麼死

我把兩堆規則攤開對照，才看出它們差在哪。

會被檢查的那些，違規全部長成同一個形狀：**某個檔案裡出現了什麼，或缺了什麼。**

檢查不了的那些，也是同一個形狀：**誰先誰後、這件事做過沒做過。**

前者是狀態，會自己留在那裡等人來看。後者是行為，發生完就結束了，除非有人特地記下來。

「同一個問題試超過 2 次必須停損」——嘗試次數不寫進任何檔案。所以沒有人能證明它被遵守過，也沒有人能證明它被違反過。

我後來發現，這不只是紀律夠不夠的問題。流程本身就沒有留下可以被檢查的完成狀態。

這是我這次真正學到的東西，而且我想把它的適用範圍講清楚——它針對的是「這一步做過沒有」、「A 必須先於 B」、「這一步不得跳過」這類規則：

> 對這種需要驗證「做過沒有」的流程規則，如果完成之後不留下任何可檢查的痕跡，就很難建立可靠的機械強制。

推論很直接：如果一條這樣的規則重要到不能只靠人記得，要改的是「讓它做完會留下痕跡」，不是把規則寫得更大聲。

Reuse Audit 需要的是一個落檔的位置，不是一句更硬的措辭。我還沒做，這篇寫的時候它仍是原樣。

### 反方向也有代價

我不主張「每條規則都該有產出檔」。

那樣做的下場很好想像：流程長出一堆只為了通過檢查而存在的檔案。最後留下的可能只是形式上的完成紀錄，卻不能代表那一步真的被做好。停損那條就是例子——為「試了幾次」造一個計數檔，成本高於它能換到的東西。

所以判斷順序是：先問這條規則值不值得為它造一個產出，再決定要不要說「不得跳過」。不是每一條都值得，但值得的那幾條，得誠實承認它現在還沒有。

**【插入：主圖——一條規則要走到「會擋」，中間要跨過什麼】**

```
  規則寫在文件裡                     ← 12 條都在這裡
        │
        ✕  Reuse Audit 卡在這一段。
        │  規則有、產出格式有、專用 subagent 也有，
        │  但做完不會留下任何檔案。9 條規則都卡在這一段。
        ↓
  做完會留下可檢查的痕跡              ← 3 條走到這裡
        ↓
  有程式在讀那個痕跡                  ← 收工檢查點讀得到帳本，但只念一句
        ↓
  不符合就退回                       ← 靜態檢查（只對新寫的檔）、CI 的索引稽核
```

這張圖不是在說每條規則都該走到最後一格。它只是說：如果我想要機械強制，中間有哪幾個條件必須先成立。

我原本以為規則和檢查程式之間是直接相連的，缺的只是工。實際上第一段就是門檻——沒有痕跡，後面兩段連開始的條件都沒有。

## 豁免名單：新債停了，舊債一行沒少

爬到最後一格也不代表事情就好了。

規則說 test 檔不能出現 `.locator()`——selector 要包在 Page Object 裡。理由是 selector 會變，包起來才改一個地方。

問題是規則上線那天，repo 裡已經一堆了。檢查程式如果一視同仁，那天所有測試都跑不了。

我的做法是加一份豁免名單：當下既有的違規全部登記赦免，之後新寫進來的一律退回。

**【插入：豁免名單的兩個數字 + 六週後的狀態】**

登記的違規是 **88 行**（收斂成 62 個特徵值[^2]），其中 `.locator()` 那一條佔 **82 行**。

一個月後我查了一次：**豁免名單建立之後新增的 test 檔，違規數全部是 0。**

這個機制有效。它確實把新債擋在外面。

但同一次查詢還有另一個結果，我一開始不想寫進來：

**那份名單從建立到現在只被改過一次，就是建立那次。六週，一行都沒少。**

所以誠實的說法是：豁免名單改變的是**新增債務的方向**，不是歷史的現實。

那 88 行還在 repo 裡，一行都沒動過。變的只是檢查程式怎麼看它們——從「違規」變成「已知、暫時不報」。所以它不會出現在任何一次檢查結果裡，包括我自己看的那些。

如果我當初同時排了每個 sprint 拔掉幾行，今天的數字不會是零。我沒排。

## 144 筆裡有 143 筆是假的

另一個方向的失敗更難看，而且是現在還在的。

我有一個編輯期的檢查點：每次改到 Python 檔，就順手稽核程式索引有沒有同步。它不是提醒，是會退回的那種。

寫這篇的時候我為了取材去跑了一次。

它退回了，吐出 **144 筆**「索引裡缺這個檔」。

其中 **143 筆是假的。**

原因是那支稽核程式用掃檔案系統的方式找 Python 檔——工作目錄底下所有的 `.py` 一律算進來。而我的工作目錄底下有一個 agent 開的臨時 worktree，沒有進版控，裡面一整包 Python 檔。

**【插入：hook 實際輸出節錄 3 行，路徑遮蔽】**

```
[missing] .claude/worktrees/agent-<略>/scripts/…
[missing] .claude/worktrees/agent-<略>/pages/…
[missing] .claude/worktrees/agent-<略>/tests/…
   （同類 141 行）
```

同一支稽核程式在 CI 上是綠的。因為 CI 是全新 checkout，那個目錄根本不存在。

同一支程式、同一天、兩個相反的答案。

而被信任的是綠的那個。

現在看到它又吐出一大串缺漏，我的第一反應已經不是「真的漏了什麼」，而是先確認這次又掃到了哪個不該掃的目錄。

也就是說，會不會擋已經不是我最先要問的問題。會退回的檢查不等於品質保證，它自己的訊號也需要可信度——而可信度來自「它看的東西，就是它要保護的東西」。這支不是：它看的是我的工作目錄，它要保護的是進到 repo 裡的內容。

我沒有修它。這篇的取材過程本身就是那個 gap 的證據；修不修是另一件事的判斷，不該由「我想寫一篇漂亮的文章」來觸發。

## 如果重來一次

三條，都是從上面幾次撞出來的。

**一、寫「不得跳過」之前，先問這一步做完會留下什麼。**

如果答案是「對話裡的一段文字」，那它現在還不是規則，是備忘。可以留著，但別叫它強制。

**二、要不要為一條規則造一個產出檔，是成本判斷，不是教條。**

值得的就做，不值得的就承認它只能靠人記得。最糟是中間那種：規則寫得很硬、實際上沒人在看，而所有人都以為有。

**三、把檢查改成「會退回」之前，先確認它看的範圍和它要保護的東西一致。**

不然本機和 CI 會對同一支檢查給出相反答案。而一個長期不準的訊號，會讓真正的違規更難從噪音裡被認出來。

## 所以現在算什麼

我不會說我建立了一套治理機制。

現在的狀態是：12 條裡有 2 條真的會擋，而我知道那 2 條為什麼擋得住、另外 9 條為什麼擋不住、其中哪幾條值得補、哪幾條不值得。

比三個月前只有一份四百多行的文件強。強的不是規則變多，是我終於分得出哪些是規則、哪些是備忘。

但這裡有一條很清楚的界線。

機械化管得住形狀，管不住證據力。

靜態檢查能確認 test 檔裡沒有 `.locator()`。但「規則有被遵守」和「測試結果值得相信」，是兩個不同的問題。

所以下一個問題更麻煩：

**規則都照跑了，測試也綠了，就代表結果是真的嗎？**

那是下一篇：《憑什麼相信 AI 說「測完了」》。
