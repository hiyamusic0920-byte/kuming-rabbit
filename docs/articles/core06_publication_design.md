# Core 06 Publication / Page Design Spec

本輪沒有改任何 HTML / CSS，也沒有動正文。以下所有決定都只描述「同一段文字要怎麼排」。

先記三件已經存在、不需要重新發明的事（讀 `styles.css` 與既有文章頁確認）：

- `.longform-standfirst` 已經存在（襯線、偏灰、不加粗、30em），但既有那篇沒用到。副標的層級不用新做。
- `.longform .article-content` 的行長是 `34em`。所有 evidence asset 都比這個寬，所以「怎麼破出行長」是本輪的核心版面問題。
- `pre` 已經支援等寬字排的縱向流程圖（`overflow-x: auto` + 1px 框）。既有那篇的 11 步 pipeline 就是這樣排的。主圖不需要新元件。

---

## 1. Publication Goal

讀者進來之後，要能在**不讀完**的情況下拿到四件事：

1. 一個具體的落差（12 條裡只有 2 條會擋）。
2. 一個真實的失敗，不是舉例（Reuse Audit）。
3. 一個判斷條件，不是口號（沒有痕跡就很難強制）。
4. 一個承認（有兩個 gap 到今天還沒修）。

版面要服務的是第 3 和第 4。第 1、2 靠正文自己就成立；容易被版面弄壞的是判斷與誠實，因為它們最像「作者在下結論」，一旦跟 source evidence 混在同一層，讀者會退回「這是他的說法」。

所以整頁的設計原則只有一條：

> **讓讀者永遠分得出，哪一塊是文件裡的字，哪一塊是我看到的，哪一塊是我推的。**

## 2. Reader Journey

### 你提的順序，我大致同意，但有一處要改

正文實際的段落順序是：

```
① 我去數了一遍                  Hook（數字現場）
② 規則寫在那裡，但沒有人在看      Reality check（12 條表 + CI 短註）
③ 有些規則⋯根本沒有東西可以驗     Deep failure（Reuse Audit）→ 判斷 → 反方向代價 → 主圖
④ 豁免名單                      Control trade-off（ratchet）
⑤ 144 筆裡有 143 筆是假的        Control failure
⑥ 如果重來一次                  Reflection
⑦ 所以現在算什麼                 Next question → Core 04
```

你的清單把 Conceptual model 列成第 4 站、獨立於 Deep failure。正文不是這樣：主圖在 ③ 的**尾巴**，是 Reuse Audit 那段推出來的結果，不是另起一站。

**我建議照正文，不要把主圖獨立成一站。** 理由是網站閱讀的：主圖如果自己開一節，讀者會把它當成「文章的架構圖」——一張總覽——然後開始問「那其他 rule 呢」。留在 Reuse Audit 之後，它讀起來是「所以剛剛那件事卡在哪」，是結論不是總覽。這正是你在 §6 說的「它不是 maturity ladder」——**版面位置就是防止誤讀的第一道措施**，比在圖下面加免責句有效。

### 兩個網站閱讀特有的問題（正文邏輯沒有，網頁上才有）

**問題一：掃讀者會先撞到表格，不是 Hook。**

網頁讀者的第一動作是滾。滾下去第一個停住眼睛的東西是那張 12 列表格——它在 ② 節中段。而三個關鍵數字（2 / 1 / 9）在 ① 節，是三個獨立段落的散文句：

```
會被擋下來的：2 條。
會在收工時被念一句的：1 條。
剩下 9 條，什麼都不會發生。
```

散文排法在紙上很好，在網頁上這三行會被當成過場，掃讀者直接滑過去。

**建議：把這三行原句排成一個三欄的數字圖（stat row），不改字。** 這不是加 marketing 數字，是把已經在正文裡的三句話給它們該有的字級。做完之後，滾到任何位置的讀者都會被這三個數字接住，然後表格變成「驗證」而不是「第一印象」。

這是本輪最重要的版面決定。

**問題二：③ 節太長，中間沒有可停的地方。**

③ 是全文重心，也是最長的一段（Reuse Audit + 兩個 H3 + 主圖）。正文已經有兩個 H3（`為什麼卡得這麼死` / `反方向也有代價`），在網頁上這兩個 H3 就是呼吸點，夠用。**不要為了「網頁段落要短」再切更多小標。**

但 ③ 節裡那句核心判斷（`> 對這種需要驗證「做過沒有」的流程規則⋯`）現在是一個 blockquote。既有 CSS 的 blockquote 是「左邊 3px 結構色線 + 灰字」——跟前面引用「設計紀錄最後一句」的那個 blockquote 長得一模一樣。

**這是本頁最危險的一處視覺撞衫：我自己的結論和文件裡的引文用同一個殼。** 見 §10，那句要換成 Interpretation 層。

### 定案的 Journey

```
Hook            數字圖（2 / 1 / 9）        ← 新增版面權重，不新增字
Reality check   12 列表（分三組）+ CI 短註
Deep failure    Asset 2（Source A / Source B / 作者註）
                → 兩個 H3 的推論散文
                → 核心判斷（Interpretation 層）
                → 主圖
Trade-off       Ratchet（最輕的排法，見 §8）
Control failure Asset 4（stat + 節錄）
Reflection      純散文，零元件
Next question   → Core 04
```

## 3. Header Hierarchy

```
Home / AI QA Lab / Core 06          ← .crumbs（既有）
我以為我寫的是規則，其實是備忘錄       ← h1 .longform-head（既有）
12 條硬規則，真正會擋下違規的只有 2 條  ← .longform-standfirst（既有，這篇第一次啟用）
2026.08.24 · 約 10 分鐘閱讀           ← .longform-meta（既有）
```

逐條回答你的問題：

| 問題 | 決定 | 理由 |
|---|---|---|
| series 要不要放 | 放，但放在 crumbs，不放 badge | 既有文章頁的 crumbs 已經在做這件事（`Home / AI QA Portfolio / 系列 03`）。系列是位置資訊，位置資訊歸麵包屑。 |
| 「Core 06」要不要 | 要，當 crumbs 最後一節 | 它是這篇在 Lab map 上的座標。放 h1 旁邊會變成編號感很重的教材。 |
| reading time 放哪 | h1 下方的 meta 行 | 跟既有那篇一致（`2026.06.23 · 約 7 分鐘閱讀`）。不要放進 crumbs，也不要在文末重複。 |
| date 是否必要 | 必要 | 這篇通篇在講「到今天還沒修」。沒有日期，那些「六週」「到今天」失去參照點。 |
| subtitle 獨立一層 | 是，用 `.longform-standfirst` | CSS 註解自己寫著「副標是報導的引言，不是第二個標題」。正文的副標本來就是引言性質，完全對上。 |
| 需不需要 deck / abstract | **不需要** | 副標已經是 deck。再加一段濃縮 thesis，讀者會連續讀到三段講同一件事的開場（副標、deck、Hook 首段），Hook 的「四百多行，我自己寫的」那個現場感會被前面兩層預告消掉。**這篇的開場力量來自敘事，不是來自摘要。** |

metadata 一律不加 badge、不加 tag chip、不加 status pill。

## 4. Reading Rhythm Map

```
①  Text  Text  Text
    ▉ STAT ROW  (2 / 1 / 9)
    Text  Text
──────────────────────────────
②  Text  Text  Text  Text
    Text（引用：盤點紀錄那句）
    Text  Text
    ▉▉ TABLE  (12 列 / 三組)
    Text  Text
    ▨ CALLOUT  (CI 短註)
──────────────────────────────
③  Text ×6
    ▉▉ ASSET 2  (Source A / Source B / 作者註)
    Text ×5
    ── H3 為什麼卡得這麼死
    Text ×4
    ▨ INTERPRETATION  (核心判斷)
    Text ×2
    ── H3 反方向也有代價
    Text ×3
    ▉▉ DIAGRAM  (主圖)
    Text ×2
──────────────────────────────
④  Text ×4
    ▪ STAT LINES  (ratchet，最輕)
    Text ×5
──────────────────────────────
⑤  Text ×5
    ▉ CODE  (143 節錄)
    Text ×5
──────────────────────────────
⑥  Text only            ← 全文唯一一節零元件
──────────────────────────────
⑦  Text only
    → Core 04
```

節奏上的三個硬規定：

1. **⑥「如果重來一次」保持零元件。** 十分鐘的文章需要一段純文字讓讀者把前面五個元件收攏。這一節不准放任何框、任何數字圖。
2. **③ 的主圖 → ④ 的 ratchet → ⑤ 的 code，是三個重元件連著來。**中間隔的散文不算多。解法不是拆散文，是**把 ④ 降級成最輕的排法**（見 §8）。所以 ratchet 不做框、不做卡片、不做 before/after 對照盒。
3. **不准有任何兩個大型元件之間少於三段散文。** 目前只有 ④→⑤ 之間接近臨界（5 段），因為 ④ 已經降級成 inline，實際上不構成連續重量。

## 5. Evidence Asset 1 — 12 Rules

素材用 `core06_public_evidence_assets.md` 的公開版（第 6 條含「（下文的 Reuse Audit）」）。

### 這張表的任務

不是讓人研究 12 條內規，是三秒看懂 2 / 1 / 9。所以**最關鍵的設計不是欄位，是分組。**

正文的列序已經是擋下 2 → 提醒 1 → 什麼都不會發生 9。不需要重排，只需要把這個既存順序**畫成三個帶**。

### Desktop

三欄表，但用三個 `<tbody>` 分組，每組一條組首列，組首帶數量：

```
規則（PROJECT_RULES 強制規則表）        做完會留下可檢查的東西嗎    現在會怎樣
━━ 會擋下來 ── 2 條 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
測試檔不能出現 .locator()                有：檔案內容              擋下
feature 的 Background 不寫登入            有：檔案內容              擋下
━━ 只會提醒 ── 1 條 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
封裝完頁面元件後必須回補共用的頁面知識      有：這次改了哪些檔        收工時提醒
━━ 什麼都不會發生 ── 9 條 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
test plan 必須在 test case 前             沒有                    —
⋯（9 列）
```

三個決定：

- **組首列取代狀態欄的視覺工作。** 第三欄的字（「擋下」「收工時提醒」）保留給無障礙與掃到單列的讀者，但字級降到 `--t-data`、不加粗；分組帶才是主要訊號。原本正文用粗體標「**擋下**」，那個粗體移到組首。
- **第三欄在第三組留破折號，不重複九次「什麼都不會發生」。** 九次重複那句在正文是 visual argument，但在**表格裡**它變成噪音——組首已經說了。（正文散文那三行的重複不動，那是另一回事。）
- **表格要破出 34em 行長**，寬到 `--shell` 的內容寬。用一個 `.evidence-bleed` 包裹層。這是全頁唯一需要新的 layout 行為。

分組帶不靠顏色：組首列用 `--surface-2` 底 + 上下 1px `--rule` + mono 標籤字。關掉顏色之後靠邊框和字體仍然分得出來。

### Mobile

**不橫捲，不 sticky column。** 12 列 × 3 欄在 390px 橫捲是最糟的解——讀者會漏掉組別，2/1/9 就沒了。

改成三個區塊，狀態當區塊標題：

```
┌ 會擋下來 ── 2 條 ──────────┐
│ 測試檔不能出現 .locator()   │
│ 有：檔案內容                │
│                            │
│ feature 的 Background 不寫登入│
│ 有：檔案內容                │
└────────────────────────────┘

┌ 只會提醒 ── 1 條 ──────────┐
│ 封裝完頁面元件後必須回補⋯     │
│ 有：這次改了哪些檔           │
└────────────────────────────┘

┌ 什麼都不會發生 ── 9 條 ─────┐
│ test plan 必須在 test case 前 │
│ 情境描述必須在頁面探索前       │
│ ⋯（9 條，只列規則）           │
│                            │
│ 這 9 條的共同點：做完不留痕跡。 │
└────────────────────────────┘
```

第三組在手機上**只列規則名，不逐條寫「沒有」**——九次「沒有」佔掉半個螢幕卻不加訊息。改成組末一句共同點（這句話是正文 ③ 節本來就有的判斷，不是新寫的 copy；如果你覺得算新增，就純粹留白，不加句）。

實作用同一份 HTML：desktop `table` / mobile `display: block` 重排，或直接兩份 markup 用 `hidden`。**建議前者**——一份 DOM，避免兩份內容日後不同步。

### 明確不做

不做排序、不做篩選、不做 hover 展開規則細節、不做 progressive disclosure。這是文章裡的證據，不是可操作的表。讀者不需要跟它互動。

## 6. Evidence Asset 2 — Reuse Audit

全文最重要的證據，也是三層必須最乾淨的地方。素材用公開版（兩塊 sanitized source + 一塊作者註）。

### 結構：你的推薦我同意，但作者註要全寬

```
┌─ SOURCE A ─── PROJECT_RULES 強制規則表 ────┐  ┌─ SOURCE B ─── 流程文件「輸出格式」段 ──┐
│                                            │  │                                      │
│ 情境描述必須在頁面探索前完成 —— 因為探索需要   │  │ ・可重用的既有項目                    │
│ 先根據情境的步驟，盤點哪些已經有現成的元件     │  │ ・缺口                              │
│ 可以重用。                                  │  │ ・每一列的信心水準                    │
└────────────────────────────────────────────┘  └──────────────────────────────────────┘

  作者註
  這一段定義了輸出的內容，但文件沒有指定輸出的檔名、路徑，也沒有定義任何代表
  Reuse Audit 已完成的產物。
```

- **Desktop 左右並排。** 這個 asset 的論證是對照——左邊要求、右邊沒說落點。並排是論證本身，不是排版偏好。兩欄等高（`align-items: stretch`），高度不齊時 Source B 底部留白，不要用內容撐高。
- **兩欄之間不放箭頭、不放 vs、不放圖示。** 對照關係由標籤和位置表達。
- **作者註全寬，橫跨兩欄下方。** 這點我要跟你的示意圖確認一次：它不能排在 Source B 底下、看起來像 B 的註腳。它是對**這一對**的觀察，不是對右邊那塊的補充。全寬 + 上方一條 1px 分隔線。
- **Mobile 垂直堆疊，順序 A → B → 作者註。** 標籤保持可見，不折疊。

### 標籤長什麼樣

`SOURCE A` / `SOURCE B`：mono、`--t-label`、字距 0.04em、大寫、放在框的左上角、壓在邊框上（negative margin，讓框線在標籤處斷開）。標籤後面接來源名，用 `--ink-faint`：

```
SOURCE A · PROJECT_RULES 強制規則表
SOURCE B · 流程文件「輸出格式」段
```

`作者註`：**中文兩個字，不寫 Observation，不寫 NOTE。** 理由：全站中文，讀者一眼認得「作者註」是誰說的；英文 label 反而要多想一秒。mono、`--t-label`、加粗，獨立成一行放在文字上方。

### Interpretation 要不要放進 asset 裡

**不要。** 這個 asset 只裝 Source 和 Observation 兩層。

正文緊接在 asset 後面的那幾句（「右邊沒有檔名」「不是難寫。是沒有東西可寫。」）就是 Interpretation，它們留在散文裡。把判斷收進框裡會產生一個很糟的效果：**框變成「完整的一份分析」，讀者可以只讀框、跳過推導過程。** 而這篇的價值恰恰在推導過程。

框裡只放我不能改的東西（source）和我看到的事實（observation）。我推出來的東西，得用散文一句一句交代。

## 7. Main Diagram

### 形狀：縱向，兩個斷點都縱向

不做橫向。三個理由：五格帶中文標籤橫排在 390px 一定要橫捲；縱向對上滾動方向；而且既有文章頁的 11 步 pipeline 就是 `pre` 縱向排的，橫向會讓這篇看起來不像同一個站。

### 一個必須做的拆分

正文的圖現在把 Reuse Audit 那段註解**排在 pre 裡面**：

```
        │
        ✕  Reuse Audit 卡在這一段。
        │  規則有、產出格式有、專用 subagent 也有，
        │  但做完不會留下任何檔案。9 條規則都卡在這一段。
        ↓
```

那是三行中文散文，在 `pre` 裡用 0.86rem mono 排。手機上這三行會超出寬度、要橫捲才讀得完——**而它是整張圖最重要的一句話。** 圖的骨架橫捲可以接受，這句不行。

**建議：字一個不改，但把它移出 `pre`，排成圖旁的一則標記。**

Desktop（骨架靠左，標記靠右對齊到 ✕ 那一列）：

```
  規則寫在文件裡              ← 12 條都在這裡
        │
        ✕ ─────────────────  ┌ 卡在這一段 ──────────────────────┐
        │                    │ Reuse Audit 卡在這一段。規則有、    │
        ↓                    │ 產出格式有、專用 subagent 也有，     │
  做完會留下可檢查的痕跡  ← 3 條 │ 但做完不會留下任何檔案。           │
        ↓                    │ 9 條規則都卡在這一段。              │
  有程式在讀那個痕跡          └─────────────────────────────────┘
        ↓
  不符合就退回
```

Mobile：骨架保持縱向不變，標記變成 ✕ 那一節底下的全寬區塊（不縮字級，用 `--t-body-s` 的**襯線**排，不用 mono）。

### 右側那些小註（`← 12 條都在這裡` 等）

保留，它們是圖的一部分，也是 §6 說的「lint / CI 要不要上圖」的答案：

- **不另外畫 lint / CI 的方塊。** 它們已經以文字形式掛在最後一格右邊（`靜態檢查（只對新寫的檔）、CI 的索引稽核`）。畫成方塊會讓圖從「條件鏈」變成「系統架構圖」，正是你要避免的。
- 四個右側小註在手機上改成每格下方的一行小字，不硬擠在右邊。

### 圖會不會過重

會，如果加：層級編號、Level 1–4、顏色分級、圖例、每格的實作物件。以上一律不加。

圖只有三種東西：五個格、四段箭頭、一個 ✕。加上圖下方正文那句「這張圖不是在說每條規則都該走到最後一格」——那句是圖的 caption，版面上要**貼著圖**（`--s-3` 間距），不要當成下一段散文（`--s-5`）。距離就是它是不是 caption 的唯一線索。

## 8. Evidence Asset 3 — Ratchet

**決定：最輕的排法。不做元件。**

理由在 §4 講過：它夾在主圖和 143 節錄之間，是全頁最不該再放一個框的位置。而且這段的力量是**轉折**（有效 → 但是），轉折用散文節奏最好，做成 before/after 對照盒反而把「但是」變成並列的一欄，張力沒了。

具體排法：正文那三個數字句已經有粗體，只把它們排成三個**貼齊左緣的獨立行**，行距放大，不加框不加底：

```
登記的違規是 88 行（收斂成 62 個特徵值），其中 .locator() 那一條佔 82 行。

    豁免名單之後新增的 test 檔，違規數 ── 0

    那份名單被改過的次數 ── 1（就是建立那次）

    六週後減少的行數 ── 0
```

三行的**句式刻意平行**、數字右對齊到同一條線。三個 0 / 1 / 0 縱向對齊時，「新債停了、舊債沒還」自己會跳出來，不需要標「正面 / 反面」的標籤。

字級用 `--t-body`，數字用 mono 加粗。不用 `--live` / `--ongoing` 上色——這一段的重點是同一個機制有兩面，上成綠紅會把它變成評分。

**明確不做**：進度條、圓餅、before/after 兩欄盒、trend line、任何「六週」的時間軸。

## 10. Evidence Grammar — Source / Observation / Interpretation

把 `core06_public_evidence_assets.md` 定的三層轉成版面規則。全站可重用，但刻意保持很小：三個 label、三種邊框，沒有 design system。

| 層 | 是什麼 | 邊框 | 標籤 | 字體 |
|---|---|---|---|---|
| **Source** | 原始內容（可 sanitized，語意不動）、實際輸出、文件引文 | **四邊全框** 1px `--rule` | `SOURCE A` / `節錄` / `PROJECT_RULES 強制規則表`（mono、大寫或原名、壓在框線上） | 中文散文用 `--f-body`；程式輸出用 `--f-mono` |
| **Observation** | 我檢查那份內容之後看到的缺口 | **無框**，上方一條 1px 分隔線 | `作者註`（mono、加粗、獨立一行） | `--f-body` |
| **Interpretation** | 我抽出的工程判斷 | **左側 3px 實線** `--structure` | `我的判斷`（mono、獨立一行）或無標籤但必在散文裡有引導句 | `--f-body`、`--ink`（不是 `--ink-soft`） |

三個關鍵約束：

1. **關掉顏色仍然分得出。** Source = 四邊框；Observation = 只有上緣一條線；Interpretation = 只有左緣一條粗線。三種邊框位置完全不同，是純結構差異。標籤是中文字，不是圖示。
2. **不靠斜體。** 斜體對 CJK 本來就是合成傾斜，難看又不可靠；而且斜體是 CSS 一改就沒的東西。
3. **既有 blockquote 樣式要退位。** 現在 `styles.css` 的 `.longform .article-content blockquote` 是「左 3px `--structure` + `--ink-soft` 灰字」——這個殼在本頁被兩種完全不同的東西共用：文件引文（Source）和我的核心判斷（Interpretation）。

   **必須拆開。** 建議：blockquote 的預設殼改給 Interpretation 用（左側粗線 + `--ink` 正色，因為那是我要讀者記住的句子），Source 的引文改走全框的 `.evidence-source`。落到本篇具體是：

   | 正文位置 | 目前是 | 改成 |
   |---|---|---|
   | ② 節「規則遵循率，原本取決於⋯」 | blockquote | Source（那是盤點紀錄的原文） |
   | ③ 節「這只能讓失敗可見，不能強制⋯」 | blockquote | Source（設計紀錄的原文） |
   | ③ 節「對這種需要驗證『做過沒有』的流程規則⋯」 | blockquote | **Interpretation** |
   | ② 節「短註：真的會擋是什麼感覺」 | blockquote | Callout（見下） |

   這是純樣式歸類，正文一字未動。但**不做這件拆分，這篇最重要的一句話會跟兩段文件引文長得一樣**。

4. **Callout 是第四種，不屬於三層。** CI 短註是題外的小故事，不是證據。給它一個獨立的輕殼：`--surface-2` 底、無框、mono 標籤 `短註`。它必須看起來比三層都輕，讀者才知道可以跳過。

## 11. Footnote Behavior

兩個 footnote，兩個都是**防誤讀的界線說明**（註 1：還有別的檢查會擋，別讀成整個 repo 只有 2 個；註 2：88 和 62 是兩件事）。

這種註的特性是：需要它的人，是**正在懷疑那句話**的人。把他送到頁尾再送回來，等於在他最挑剔的那一秒把他移出文章。

**決定：inline `<details>`，收合。**

```
註 1 —— 那張表以外還有哪些會擋 ▾
```

- 用原生 `<details>` / `<summary>`，零 JS。站上 `.portfolio-card summary` 已經有 `<details>` 的用法，這個模式不是新發明。
- `summary` 用 mono、`--t-body-s`、`--ink-soft`，前面帶 `註 1 ——` 標記。展開後內容用 `--f-body`、縮排一格、上方細線。
- 展開/收合不做動畫（`--dur-slow` 這裡沒用，高度動畫容易在手機上抖）。
- **不做 hover popover。** 手機沒有 hover，會退化成「點了跳走」，等於沒設計。
- **不做頁尾 footnote 區塊。** 兩則而已，開一個 appendix 區會讓文章看起來附了技術附錄——正是你要避免的。
- 手機上 `summary` 的可點區域至少 44px 高（站上 `.crumbs a` 已經在用 `min-height` 的做法）。

代價要說清楚：`<details>` 收合的內容**不會被瀏覽器內建搜尋找到**，也不會出現在列印版。這兩則註都不是必讀，我判斷可以接受。

## 12. Mobile Behavior

四個最容易爆掉的元件，逐個講具體怎麼變。斷點跟站上一致，用 900px。

### ① 12 列表格

`table` → `display: block` 的三個區塊。狀態變成區塊標題並帶數量；第三組只列規則名。**不橫捲、不 sticky、不縮字。** 詳見 §5。

破出行長的 `.evidence-bleed` 在手機上失效（本來就是滿寬），左右保留 `--s-4` 內距，字不貼邊。

### ② Asset 2 左右對照

`grid-template-columns: 1fr 1fr` → `1fr`，垂直堆疊，順序 A → B → 作者註。

**兩個框之間的間距要放大到 `--s-5`。** 桌機靠左右分隔就知道是兩份不同來源；手機上兩個框上下相鄰、間距一樣時，讀者會以為是同一份的續篇。間距是手機上唯一的分隔線索，不能省。

標籤 `SOURCE A` / `SOURCE B` 一律保留可見，不折疊、不縮成 `A` / `B`。

### ③ 主圖

骨架維持縱向 `pre`，允許橫捲（五個格的中文標籤最長約 10 字，360px 大致放得下，超出讓它捲）。

Reuse Audit 那則標記**移出 `pre`**，變成 ✕ 那一節下方的全寬區塊，用襯線 `--t-body-s`，不橫捲。這是 §7 那個拆分在手機上的主要收益。

右側四個小註改成每格下方一行 `--t-data` 小字，縮排對齊格子文字。

### ④ 節錄 code block

允許橫捲，這是唯一該橫捲的元件（內容是路徑）。

- 不縮字級到 0.7rem 以下（0.8rem 是底線）。
- 不加行號（吃掉寬度、也不需要引用某一行）。
- 三行 `[missing]` 的行首不縮排，讓「三行都是同一類」在不捲的情況下就看得出來。
- 捲動容器要有 `-webkit-overflow-scrolling: touch`，並確認外層 `body` 不會跟著橫向捲（`.evidence-bleed` 要 `overflow-x: hidden` 在 wrapper 層之外）。

### 手機上的整體防塞規則

不准出現「表格 → 圖 → 表格」連續三個元件。目前的順序在手機上展開是：

```
STAT ROW → 表格三塊 → callout → Asset 2 三塊 → 主圖 → stat lines → code
```

中間都有散文隔開，最擠的是 Asset 2 三塊接主圖，隔了五段散文加一個 H3，可以接受。**但 §8 的 ratchet 一旦改成有框的元件，手機上就會變成主圖 → 框 → 框連三個。這是我堅持 ratchet 不做框的第二個理由。**

正文最後一節「所以現在算什麼」已經自己丟出下一個問題（規則有被遵守 ≠ 結果值得相信）。文末導航只要接住它，不要再介紹。
