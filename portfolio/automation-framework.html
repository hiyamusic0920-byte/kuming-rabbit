01 · 分層架構

每一層只做一件事

分層的目的不是好看，是讓畫面改版、規格變更、測資失效這三種壞掉的原因，各自只打到一層。

圖較寬，手機上可左右滑動。

各層職責與邊界

1

Test Plan 先於 test case。先決定每個情境走 unit / API / E2E / manual 哪一層，再展開案例。沒有這一步，所有決策分支都會被推成 E2E，跑很久又很脆。

2

step definition 不寫 selector。tests/test_OWxxxx.py 只呼叫 Page Object 的方法。這條有 lint 擋，不是口頭約定。

3

Page Object 不寫業務判斷。它只負責「怎麼操作這一頁」和「這一頁現在顯示什麼」，斷言留在測試層。

4

Component 等第二個入口出現才抽。同一組 UI 元件從兩個以上入口重複出現才抽成 Component（例如日期選擇器、訂單列表搜尋）。只被一張票用到就先留在 Page Object，避免一開始硬拆到很細。

5

跨頁流程才叫 flow。例如「完整訂房」「建立訂單到入住」。單張功能票不把登入、切旅館、造資料全塞進每個情境。

02 · selector 管理

踩過的坑要寫回 repo，不能只留在腦袋裡

Page Object 收的是「怎麼點」，但真正會讓下一個人重踩的是「為什麼這樣點才會成功」。這類知識另外存成 registry。

目前 pages/_registry/ 有 42 份頁面筆記，每份記的是非顯而易見的部分：selector 為什麼要這樣寫、要等什麼條件才算載入完成、哪個互動有陷阱、頁面依賴哪個狀態。普通又自明的 locator 不進 registry，只留在 Page Object 的程式碼裡，避免 registry 變成翻譯一次程式碼。

為什麼要獨立成文件：這個 repo 是人和多個 AI agent（Claude Code、Codex）一起工作的。agent 之間不共享對話記憶，寫在 chat 裡的結論下一個 session 就沒了。知識只有進 repo 才會被下一個執行者讀到。這條規則也反過來約束 AI：用瀏覽器實機測完票，走過的頁面沒回補 registry，就算這張票的知識回補沒做完。

實際會記進去的，例如 Element UI 的日期元件直接 fill 或模擬鍵盤都不會生效，要直接設底層 form 的欄位值；或是某個列表要等某個 API 回來才算穩定，用固定秒數等會隨機失敗。

03 · 測試資料

前置資料走產品的真實 API

測試資料是自動化最容易爛掉的地方。這裡的原則是：寧可建得慢一點，也不要建出產品不可能產生的狀態。

不自己捏單號、不直接塞 DB

訂單編號由後端發。自己組編號塞進資料庫，建出來的是產品流程不會出現的狀態，測過也不代表真的會動。

seed factory 自動找可用條件

自動找可建單日期、計算房量、建立測試訂單，不會因為日期被別人用掉就整批失敗。

驗證要看到前端

只看讀取 API 回傳的狀態碼不算驗過，要在實際頁面上看到那筆資料呈現正確。

環境切換集中一處

dev / release 的連線一律走 config/settings.py，不在個別 script 裡各自讀環境變數。

04 · 執行穩定性

三條防線，擋住「跑很久卻換不到報告」

這三條是踩過才加的。有一次同一張票跑了四輪、超過 70 分鐘，一份可用報告都沒有，其中一輪跑了快 11 分鐘換到 43 個 skip，而且退出碼是 0——綠的。

1

批次層前置條件在 session 層驗一次，不成立就硬失敗。旅館有沒有可建單日期、token 有沒有過期、環境通不通，這些在開跑前驗，不要寫在單一測試檔裡——否則環境沒 token 時，連收集測試都會紅成一片，看不出真正原因。單一案例自己的 skip 不受影響。

2

一次執行選中的案例全部 skip，判定為失敗。由 conftest.py 自動判定。全 skip 產出 0 筆證據，不能算通過，但預設的退出碼會是 0，很容易被當成跑完了。

3

當天第一次全量帶 --maxfail=5。參數化超過 12 組的矩陣型測試，全量前先跑涵蓋各軸的子集。目的是早點知道是不是環境壞了，而不是等 40 分鐘才發現全錯。

共同的判斷：自動化測試真正的成本不是寫，是「跑完才發現這輪不算數」。所以這三條都在換同一件事——讓無效的執行越早停越好。
05 · 報告產出

測試只產資料，PDF 另外產

pytest 不直接產 PDF。它只產一份合約 JSON，通過驗證後才手動渲染成 PDF。這樣手動驗收和自動化測試可以共用同一條報告管線。

同一次測試，兩份報告

同一份 JSON 渲染成兩種版型。QA 版給工程端，每一步帶實際結果和 API 證據檔路徑，出問題可以照路徑翻出原始回應；UAT 版給業務驗收，只留驗收步驟和預期結果，連 TC 編號都拿掉。

一個細節：報告的「實際結果」欄不准填罐頭字。寫「如預期」等於沒驗，所以驗證腳本會擋下來，要求填真正量到的值。截圖全白也會被擋。
06 · 規範把關

寫法規範自動擋，不靠人工 code review

規範寫在文件裡沒人會記得。能寫成檢查的就寫成檢查，掛在對應的步驟上。

檢查擋在哪擋什麼
test plan lint寫測試策略時欄位缺漏、沒寫分層判斷
test case lint寫測試案例時格式與抽象層級，例如步驟寫成點哪個按鈕而不是業務行為
測試寫法 lint寫 Page Object 時寫死 selector、Page Object 裡寫業務判斷
step 綁定檢查綁 BDD 步驟時feature 的步驟沒綁到對應的 step definition
批次層檢查執行時前置條件不成立、整批 skip
報告驗證產報告時schema 不合、實際結果是罐頭字、截圖空白
索引稽核收尾時新增的 Python 檔沒登記進索引
git pre-commit hookcommit 時資料庫連線資訊被 commit 上去
07 · AI agent 怎麼接進來

先有規則和知識，AI 才接得上

上面這些分層、registry、lint 和報告合約，不只是給人用的。它們是 AI agent 能接手測試的前提：規則寫成程式，AI 才有東西可以照著走、也才擋得住。

核心原則是「agent 可以換，repo 才是真理來源」。規格、selector、測資策略、報告合約都寫在 repo 裡，Claude Code 和 Codex 讀同一份知識，換工具或換模型都不用重教。目前每個 sprint 可測的票有六成以上交給 AI 執行。
