如何從無限輸入建立可測試的 Test Model？

問題不是 Test Case 不夠多，而是可能性太多

2026.08.27 約 16 分鐘閱讀
← 返回 Portfolio 上一篇：Coming Soon 下一篇：Coming Soon

最近面試時，我被問了一個乍聽之下很基礎的問題：

Test Case 怎麼設計？

我第一個反應其實是：

咦？怎麼會問這麼初階的問題？

所以我開始回答需求分析、風險評估、測試策略、如何決定 coverage。

但聊到後面，我才發現，他們真正想問的可能不是「Test Case 怎麼寫」。

而是：

假設有 30 個 API，彼此有些相關、有些不相關，而且使用者很可能不按照說明書操作，要怎麼設計測試？

這就完全是另一回事了。

之前在測試 AI Chatbot 時，我也遇過幾乎一樣的困境：

使用者什麼都可能輸入，那我要準備哪些 Test Case？

「正常問法、錯字、資訊不足、答非所問、惡意輸入、多輪對話……」

如果沿著每一句使用者可能說的話一直列，一樣永遠列不完。

後來真正需要解決的，也不是「再多想 100 句 Prompt」，而是先定義：Chatbot 的 Input Space 可以拆成哪些測試維度？

這其實就是同一個問題本質。

→「我如何測試 AI Chatbot？」會在後面系列文獨立說明。

問題：不是 Test Case 不夠，而是可能性太多

假設今天有一個 SDK。

文件告訴使用者，正確操作方式是：

Install Dependency
↓
Initialize SDK
↓
Load Model
↓
Create Session
↓
Run
↓
Release

如果所有使用者都乖乖照說明書操作，其實很好測。

問題是真實世界不會這麼美好。

有人可能沒裝 Dependency 就直接 Initialize：

Missing Dependency
↓
Initialize SDK

有人裝了不相容的版本：

Wrong Dependency Version
↓
Initialize SDK
↓
Run

也有人完全不按照預期順序：

Initialize
↓
Run
↓
Load Model
↓
Initialize again
↓
Release
↓
Run again

如果系統裡還有 30 個 API，QA 很自然會想到：

那就把各種情況全部列出來？

但很快就會發現：

根本列不完。

就算真的列完了，也測不完。

光是假設每次測試只考慮：

5 種 Environment
×
5 種 Dependency State
×
30 個 API
×
5 種 Input State

就已經有 3,750 個基本組合。

而這還只挑了四個維度。

設定檔寫錯、API 彼此的呼叫順序、前後狀態，全都還沒算進去。

一旦開始考慮這些關係，測試空間只會繼續膨脹。

這時候問題已經不是：

QA 寫 Test Case 的速度能不能再快一點？

甚至也不是：

我們怎麼加入 AI，讓它幫忙產生更多 Test Case？

而是：

我們是不是一開始就不該用「窮舉 Test Case」的方式理解這個問題？

從設計 Test Case，變成設計 Test Case Generator

以前 QA 做 Test Design，很自然會問：

這個功能，我要測哪些 Case？

於是我們讀需求、理解 Business Rule、找 Boundary、想 Exception，最後產出一組 Test Case。

這件事沒有錯。

但當測試空間大到人類無法窮舉，而 AI 又加入之後，問題開始改變了。

我們除了問：

我要設計哪些 Test Case？

還可以往上一層問：

我要設計一套什麼規則，才能持續產生值得測的 Test Case？

也就是從：

QA
↓
Design Test Cases
↓
TC001
TC002
TC003

變成：

QA + AI
↓
Build Test Model
↓
AI explores the model
↓
Generate Test Cases

這兩個詞後面會一直出現，先把差別講清楚：

Test Model
＝ 資料
維度、值、狀態、API 之間的關係

Generator
＝ 規則
拿這份資料，推導出該測哪些組合

Model 描述受測物件長什麼樣子。

Generator 決定要從裡面挑什麼出來測。

這裡的 Test Case Generator 不是一句：

幫我產生完整的 Test Case。

而是一套明確的方法：

輸入什麼資訊？
↓
怎麼拆測試維度？
↓
怎麼判斷 API Relation？
↓
有哪些 Constraints？
↓
哪些 Combination 有意義？
↓
怎麼判斷 Risk？
↓
哪些 Combination 要變成 Test Case？

以前 QA 靠大量壓縮的經驗，把自己的判斷直接寫成 Test Case。

現在，我們可以嘗試把產生這些判斷的方法也設計出來。

這個差別很重要。

因為一組 Test Case 解決的是：

這一次我要對受測物件測什麼？

而一個好的 Generator 解決的是：

下一次需求改變、API 增加、Environment 改變時，我們要如何重新推導「該測什麼」？

先畫出測試空間

第一步先整理：

有哪些因素會改變系統行為？

以那個 SDK 為例，我第一版是這樣寫的：

Environment
├── OS
├── Runtime Version
└── Hardware

Installation
├── Correct
├── Missing Dependency
├── Wrong Version
└── Wrong Configuration

Usage
├── Normal Sequence
├── Skip Step
├── Wrong Order
├── Duplicate Call
└── Retry After Failure

Input
├── Valid
├── Invalid
├── Boundary
├── Missing
└── Wrong Type

看起來很整齊。

問題來了。

我們怎麼知道自己這樣分是合理的？

這時候 MECE 就可以拿來當成一個檢查方法。

MECE（Mutually Exclusive, Collectively Exhaustive）原本就是在處理一件事：

當一個問題很大、很複雜，我們把它拆小之後，要怎麼檢查自己是不是一直在描述同一塊，卻漏掉另外一整塊？

放進 Test Design 裡，我會把它變成三個問題：

  • 我現在用什麼維度拆這個問題？
  • 同一個維度裡，有沒有重複或混雜？
  • 有沒有重要的情況，根本沒有被分進來？

拿這三個問題回頭檢查上面那張圖，我自己就先不及格了。

第一，Installation 底下混了兩個維度。

Missing Dependency、Wrong Version 講的是相依套件裝成什麼樣子。

Wrong Configuration 講的是設定檔寫成什麼樣子。

這兩件事互相獨立。套件可以裝得完全正確，設定還是寫錯。

把它們塞在同一層，等於在說「套件對但設定錯」這種情況不存在。

但那正是真實世界最常出事的一種。

第二，Environment 那格的型別不對。

Installation、Usage、Input 底下列的是值。

Environment 底下列的 OS、Runtime Version、Hardware 是三個子維度。

一個列值、一個列維度，混在同一張圖上，後面拿它們相乘就會算錯。

拆完之後長這樣：

Environment
├── macOS
├── Ubuntu
├── Windows
├── Container
└── CI Runner

Dependency State
├── Correct Version
├── Missing
├── Wrong Version
├── Partially Installed
└── Conflicting Package

Configuration State
├── Valid
├── Missing Required Field
├── Invalid Value
└── Pointing to Wrong Resource

Usage
├── Normal Sequence
├── Skip Step
├── Wrong Order
├── Duplicate Call
├── Retry After Failure
└── Concurrent Call

Input
├── Valid
├── Invalid
├── Boundary
├── Missing
└── Wrong Type

從四個維度變成五個。

多出來的那一個不是為了讓圖好看。

而是原本有一整塊組合，我根本看不見。

我們不是在宣稱：

這些狀態已經包含世界上所有 Bug。

而是先建立一個可以討論、可以檢查、可以持續補充的測試空間。

這件事情在 AI 加入之後反而更重要。

因為以前 QA 一天可能只寫 30 條 Test Case。

現在 AI 很快就能給你 300 條。

問題已經不是 Case 不夠多，而是：

這 300 條是不是其實一直在測同一塊？

以及：

有沒有一整塊測試空間，AI 從頭到尾根本沒想到？

而這件事是可以數的。

只要每一條 Test Case 都標回它來自哪個維度、哪個值，就能直接列出來：

Input = Boundary                        →  88 條
Dependency State = Conflicting Package  →  41 條
Usage = Concurrent Call                 →   2 條
Dependency State = Partially Installed  →   0 條   漏測
Configuration State = Invalid Value     →   0 條   已排除

哪一格被打爛、哪一格是零，一眼就看得出來。

但零有兩種意思，一定要分開。

一種是真的沒人測到。

另一種是那個組合被 Constraints 排掉了。它本來就不成立——例如套件根本沒裝的時候，設定檔指到哪裡已經沒有意義。

這兩種在表上長得一模一樣，都是零。

分不出來的話，你會花力氣去補一塊其實不用補的，而真正的漏洞還躺在旁邊。

所以這張表一定要有第三欄，標清楚那個零是「已排除」還是「漏測」。

所以建立 Test Model 的目的，不是讓分類看起來漂亮。

而是讓我們開始有辦法回答：

我們到底正在 Cover 哪裡？

但分類本身，也不應該全部丟給 QA

這裡又會遇到另一個現實問題。

如果今天真的有 30 個 API、一大包 SDK 文件、不同 Environment 和 Dependency，而我們告訴 QA：

好，現在請你先把所有 Dimensions、States、Relations 全部整理好，再交給 AI。

好像也沒有真的解決人工瓶頸。

只是把工作從：

人工寫 Test Case

搬成：

人工寫 Test Model。

所以比較合理的做法應該是：

API / SDK Spec
Documentation
Known Business Rules
Existing Tests
        ↓
AI 建立 Test Model Draft
        ↓
QA Review
        ↓
修正 / 補充 / 確認
        ↓
Approved Test Model

AI 可以先從現有資料裡整理：

Dimensions
Values / Partitions
States
API Relations
Preconditions
Constraints
Unknowns

但它不能看到 API 名稱，就自己腦補：

Run 看起來應該需要 CreateSession，那我就當成 Dependency。

每一個 Relation 都應該盡可能回答：

Relation:
Run requires CreateSession

Evidence:
SDK Documentation / Spec

Status:
Confirmed / Assumed / Unknown

AI 負責大量整理，QA 負責決定這張地圖能不能相信。

這才真的有省到人工。

怎麼從無限組合縮成值得測的組合？

有了 Test Model 之後，才開始處理 30 個 API。

第一件事情不是：

API 1 × API 2 × API 3 × ... × API 30

因為有些 API 有關係，有些根本沒有。

例如：

Initialize
    ↓
Load Model
    ↓
Create Session
    ↓
Run
    ↓
Release

這幾個 API 明顯存在關係。

Run 可能要求 Session 已經存在。

Create Session 可能要求 Model 已經載入。

Release 之後再呼叫 Run，系統也應該有明確的行為。

但是：

Get SDK Version

可能根本不需要跟 Release 做大量排列組合。

所以我們可以先建立 API Relation Map：

API A
│
├── data dependency → API B
│
├── state dependency → API C
│
└── sequence dependency → API D

API E
└── independent

先問：

哪些 API 組在一起，真的可能讓結果發生變化？

接著，再故意破壞這些 Relation。

正常流程：

Initialize
↓
Load Model
↓
Run

Generator 就可以從 Relation 推導出不同情境。

1. Skip

未 Initialize → 直接 Run
2. Wrong Order

Initialize → Run → Load Model
3. Duplicate

Initialize → Initialize again
4. State Violation

Initialize → Load Model → Release → Run

這時候我們不是叫 AI：

幫我多想一些奇怪的 Test Case。

而是給它一條生成規則：

找出 API Relation，再探索正常 Relation 與破壞這些 Relation 時，系統應該如何反應。

這就是 Generator 開始出現的地方。

接著才進入 Combination。

例如 Run 同時受到三個維度影響：

Dependency State
        ×
API Sequence
        ×
Input State

對回前面那張圖：

Dependency State = 5
API Sequence     = 6
Input State      = 5

完整組合就是 150 種。

我們仍然不需要全部測。

可以先用 Constraints 排除根本不成立的組合，再根據不同的測試目的，例如：

  • Interaction Coverage，例如 Pairwise
  • Boundary
  • State Transition
  • Business Risk
  • 歷史 Bug
  • Error Recovery

挑出值得驗證的交叉點。

但還有一個條件很容易被漏掉：這個組合架不架得起來。

「裝一組互相衝突的套件版本」、「Release 之後再 Run」——光是把環境擺成那個樣子的成本，常常比想出這條 Case 還高一個量級。

所以挑選的時候要同時看兩件事：

這條 Case 值多少？  ← Risk
架起來要花多少？    ← Setup Cost

高風險又便宜的，先做。

高風險但很貴的，要嘛想辦法讓它變便宜，例如寫一支能一鍵造出壞環境的腳本；要嘛就誠實承認這一輪不測，並且記下來。

沒記下來的話，過三個月沒有人分得出來，那塊到底是「決定不測」還是「忘了測」。

整個 Generator 的流程就會變成：

API / SDK Spec
      ↓
Build Test Model Draft
      ↓
QA Review / Approve
      ↓
Approved Test Model
      ↓
Define Constraints
      ↓
Generate Combination Space
      ↓
Select by Coverage / Risk
      ↓
Generate Test Cases

Test Case 是這套 Generator 的 output，而不是起點。

產得出 Case，不代表判得出對錯

到這裡為止，Generator 解決的都是同一個問題：

要測哪些組合？

但還有一個問題完全沒被解決：

這個組合跑出來，我怎麼知道它是對的？

例如剛剛那條：

未 Initialize → 直接 Run

系統應該回什麼？

丟一個明確的錯誤碼？直接 crash？還是靜默回一個空結果？

spec 通常不會寫。

這件事很現實。

Generator 一個晚上可以產 300 條 Case，但如果每一條的預期結果都是空的，QA 還是得一條一條想。

人工瓶頸沒有消失，只是從上游搬到下游。

所以預期結果必須在 Test Model 階段就一起標，而不是等 Case 產完才想。

我會把它分成三類：

Specified
spec 明確寫了應該發生什麼
→ 直接當斷言

Baseline
spec 沒寫，但系統現在的行為是已知的
→ 先把現況錄下來當基準線
→ 之後只驗「有沒有變」

Unknown
spec 沒寫，現況看起來也不合理
→ 這條不是 Test Case
→ 是一個要拿去問 PM 或 RD 的問題

第三類其實是整套流程的意外收穫。

一條「連預期結果都定不出來」的組合，往往就是規格真的有洞的地方。

以前這種洞，要等到上線後被使用者踩到才會浮出來。

Generator 之外，還要有人稽核 Generator

Generator 負責的是：

Source
↓
Model Draft
↓
Human Approved Model
↓
Combinations
↓
Test Cases

它的目標是：

產生值得測的案例。

Auditor 則不沿用 Generator 的結論直接往下檢查。

它要重新回到 Source：

Spec / Documentation
        ↓
重新檢查 Dimensions
        ↓
Relation 有沒有 Evidence？
        ↓
有沒有 Unknown Relation？
        ↓
重要 State Transition 有沒有 Cover？
        ↓
高風險 Interaction 有沒有 Case？
        ↓
是否大量 Case 重複 Cover 同一區？

它的目標是：

找 Generator 沒看到的地方。

所以 Generation 和 Audit 不只是換一個 Prompt。

更重要的是：

Auditor 不能把 Generator 的答案直接當成事實。

否則還是：

AI 自己出題，再自己告訴你自己考了 100 分。

不過這裡要誠實一點。

「回到 Source 重新檢查」只擋掉了一半的問題。

它擋掉的是推理被污染——Auditor 不會因為看過 Generator 的答案，就順著它的邏輯往下想。

但它擋不掉另一半：共同盲區。

Auditor 讀的是同一份 spec，用的是同一個模型。

同一句話它一樣看不懂，同一個隱含假設它一樣沒想到。

所以「Auditor 沒抓到任何問題」這個結果，其實沒有資訊量。

你分不出來是真的沒問題，還是兩邊一起瞎。

要讓 Audit 真的有價值，Auditor 必須拿到 Generator 沒有的東西：

歷史 Bug 清單
實際執行結果
客服回報 / 使用者實際操作紀錄
程式碼本身

只要有一項是 Generator 看不到的，Audit 才算真的從另一個角度看同一件事。

Approved Model 會過期

還有一個代價要先講清楚。

Approved Model 一旦被人審過、簽過，它就變成一份會被信任的文件。

問題是 spec 會改。

spec 一改，那些 Relation 底下的 Evidence 就過期了。

如果沒有人負責重審，第二個 sprint 之後，你會有一份沒人敢用、但大家還是一直在引用的 Model。

那比沒有 Model 更糟，因為錯誤會被當成事實往下傳。

所以 Model 要當成程式碼在管：

進版控，看得到 diff
每一條 Relation 帶「證據來源 + 最後確認日期」
spec 有異動時，列出受影響的 Relation 清單，要人重新確認

這件事不做，前面那套 Generator 撐不過三個月。

一套可以開始實驗的方法

如果把整件事情整理成一個最小的方法，我目前會把它畫成：

              HUMAN QA
                 │
          定義目標 / Risk
                 │
                 ▼
        ┌─────────────────┐
        │ GENERATOR SKILL │
        │                 │
Source →│ Build Model     │
        │ Find Relations  │
        │ Mark Unknowns   │
        └────────┬────────┘
                 │
                 ▼
             QA REVIEW
                 │
       校正 / 補充 / Approve
                 │
                 ▼
          APPROVED MODEL
                 │
                 ▼
        ┌─────────────────┐
        │ GENERATOR SKILL │
        │                 │
        │ Combination     │
        │ Selection       │
        │ Generate Cases  │
        └────────┬────────┘
                 │
                 ▼
             TEST CASES
                 │
                 ▼
        ┌─────────────────┐
        │  AUDITOR SKILL  │
        │                 │
Source →│ Re-check Model  │
        │ Coverage Gap    │
        │ Unsupported     │
        │ Unknown         │
        └────────┬────────┘
                 │
                 ▼
              QA REVIEW
                 │
                 ▼
              實際測試
                 │
                 ▼
          Actual Evidence
                 │
                 └──────→ 修正 Model / 下一輪

人在這裡沒有消失。

AI 擅長的是：

大量整理、展開 Combination、比對 Coverage、找出候選組合。

QA 負責的是：

確認分類是否合理、Relation 是否可信、判斷 Risk，以及決定 AI 的推論能不能進入正式 Model。

不用先蓋 AI Testing Platform，先做兩個 Skill

如果一個 QA 團隊想開始實驗，我反而不建議一開始就做一套很大的 AI Testing Platform。

先做兩個最小的 Skill。

Skill 1：Test Model & Case Generator

它不是拿到 Spec 就直接吐 Test Case。

第一階段先建立 Model：

Input

API / SDK Spec
Documentation
Business Rules
Known Constraints
Existing Tests

輸出：

Test Dimensions
Values / Partitions
States
API Relation Map
Constraints
Unknown Relations
Evidence

經過 QA Review 之後，再進第二階段：

Approved Test Model
↓
Combination Candidates
↓
Coverage / Risk Selection
↓
Selected Test Cases

而且每一條 Test Case 都必須能回答：

我是從哪個 Dimension × Relation × Rule 推導出來的？

這樣 Case 才是可追溯的。

Skill 2：Test Design Auditor

輸入：

Source Spec / Documentation
Approved Test Model
Generated Test Cases

Auditor 不負責再生一批 Test Case。

它重新從 Source 出發，挑戰：

有沒有漏掉 Dimension？
Relation 有沒有 Evidence？
哪些 Relation 只是 Assumption？
有哪些 Unknown？
哪些重要 Combination 沒 Cover？
哪些 Case 其實重複？
High Risk 區域是否反而 Coverage 很低？

最後輸出：

Coverage Gaps
Unsupported Assumptions
Unknown Relations
Duplicate Coverage
Recommended Experiments

下一步，實驗方法論

做到這裡，方法論還只是方法論。

下一個最小行動應該是：

拿 3～5 支真的有 Relation 的 API，開始實驗。

而且不要一次證明所有事情。

第一輪只驗證：

AI 能不能從真實 Spec 建出一份 QA 認為可用的 Test Model Draft？

如果連 Model 都建不好，後面的 Test Case 根本不用談。

不過「可用」這兩個字沒辦法量。

實驗跑完，如果結論只有「感覺還行」，那就不叫實驗。

所以我會把它換成三個可以數的數字：

QA 改了幾個維度、幾條 Relation？     ← 越少越好
AI 漏掉幾條我本來就知道的 Relation？  ← 越少越好
AI 掰了幾條根本不存在的 Relation？    ← 這個最致命

第三個數字如果高，代表 Generator 現在產的東西不能信。

那就要先回頭修「每條 Relation 都必須標 Evidence 和 Status」這條規則，而不是急著往下跑 Test Case。

下一輪的目標很單純：這三個數字要往下掉。

如果可以，再驗證第二件事：

從 Approved Model 產生的 Test Case，有沒有找到人工原本沒想到、但合理的重要 Combination？

最後才驗證 Auditor：

它能不能真的找到 Generator 漏掉的東西？

也就是：

Experiment 1
Model 能不能用？
        ↓
Experiment 2
Cases 有沒有價值？
        ↓
Experiment 3
Auditor 抓不抓得到盲區？

一次只驗證一個假設。

如果實驗結果不好，就修 Generator 或 Model。

如果實際執行測試後發現新的 Relation、Constraint 或 State，也把 Evidence 回寫到 Model，再進下一輪。

這時我們測試的其實不只是 API。

我們也正在測試自己的 Test Case Generator。

而這可能才是從：

「讓 AI 幫我寫 Test Case」

走到：

「讓 QA 設計一個可以被驗證、可以持續改善的 AI Test Design System」

真正的第一步。
