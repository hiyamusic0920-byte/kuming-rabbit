QA / UAT PDF → 交給稽核方

◆ = 人類必須決策，AI 不得自行通過。
三個節點：測試範圍、測試案例、報告定稿。

  • 為什麼是這三步

    這三步錯了，後面全部白做。測試範圍定錯，就是把力氣花在不重要的地方；測試案例沒審，等於讓 AI 自己決定什麼叫測過了；報告沒定稿，錯的結論會直接進到稽核文件。

    起源：第 13 話 · 第 10 話

  • 固定交付物，可變測試深度

    每張票都產出同一組東西：test plan、test cases、feature 檔、測試腳本、證據 JSON、PDF 報告、worklog。深度看票的風險調整——低風險的票不必補完整 E2E，但交付物的欄位不能少，否則報告格式會跟著漂。

    起源：第 05 話

  • 一個大 prompt 拆成多個可觀察的步驟

    把整件事丟成一個指令，壞掉的時候你不知道是哪一步壞的。拆成步驟之後，每一步都有輸入和輸出，出問題可以指到某一步重跑。

    起源：第 05 話

Architecture

誰在跑、資訊往哪流、什麼東西橫跨全部。

三層來看比較清楚：上面是誰在跑，中間是資訊怎麼流，旁邊是不屬於任何一步、但每一步都會用到的東西。

誰在跑

  • Human Sunny · QA-PM

    下票、定範圍、審測試案例、報告定稿。兩個 agent 意見不同的時候，我是仲裁的人。

  • Agent · Lead 苦命兔 · Claude Code

    預設的執行者，可以叫另一個 agent 來討論。跑主線流程、寫腳本、出報告。

  • Agent · Peer 苦力怕 · Codex

    對等的第二個 agent，不是下屬。個性偏減法，常常拆掉前一個 agent 想加的東西。

資訊往哪流

  1. 01

    票進來

    需求票加上 repo 裡已經有的產品知識，組成這次工作的上下文。這一步做不好，後面十步都在猜。

    進：需求票、產品知識、既有測試資產　出：test plan

  2. 02

    設計與探勘

    測試案例先審過，才去真實瀏覽器上確認畫面元素怎麼抓。selector 封裝進 Page Object，不散在腳本裡。

    進：test plan　出：test cases、feature 檔、Page Object

  3. 03

    執行與收證

    跑測試的同時自動收步驟截圖，結果寫成固定格式的 JSON。證據不是事後補的，是跑的時候就落下來的。

    進：測試腳本、測試資料　出：證據 JSON、步驟截圖

  4. 04

    交付與回饋

    統一的 renderer 讀證據 JSON 產出 PDF。這一步還有一件事常被忽略：這次學到的東西要寫回 repo，不然下次重新踩一次。

    進：證據 JSON　出：QA / UAT PDF、worklog、回寫的知識

Knowledge · 橫跨每一步

商業規則、UI 陷阱、測資、決策紀錄。四步都在讀它，第四步會寫回它。

  • 產品知識與商業規則
  • 頁面與 selector 的踩坑紀錄
  • 測試資料怎麼造
  • 跨 agent 討論的結論

Governance · 橫跨每一步

共用規則檔。兩個 agent 讀同一份，所以規則只需要維護一次。

  • 硬規則與禁止行為清單
  • 停止條件（什麼時候該停下來問）
  • 權限邊界（哪些檔案不准動）
  • 人類決策節點

Agent 可換，repo 才是真理來源。聊天記錄和模型的記憶都不是。

Governance

規則檔寫的多半是「不准做什麼」。

一開始我以為要教它怎麼做才對。後來發現有用的規則幾乎都是反面的：什麼時候要停、什麼不能碰、什麼要先問。

  • 停止條件

    失敗重試三次就標記成不穩定並停下；不准直接改腳本，要先分析可能原因；修正後第一次失敗就停，交人判斷。沒有停止條件的話，它會一直加等待時間，把不穩定包起來而不是解掉。

    起源：第 06 話 · 完整紀錄 →

  • 權限邊界

    哪些檔案不能動、哪些資料夾不准整理、哪些修改要先問。這條是被逼出來的——它「順手幫忙整理」過一次之後。

    起源：第 07 話 · 完整紀錄 →

  • 人類決策節點

    規則存在，不等於規則會被引用，不等於規則會被遵守，也不等於它知道下一步該做什麼。所以重要的地方要設節點讓它停下來，而不是相信它會自己想起來。

    起源：第 13 話 · 完整紀錄 →

  • 變更要可追溯

    規則被改過就要看得出來是誰改的、為什麼改。這條的起因不是 AI 亂改，是我自己改了規則然後忘記為什麼——所以決策要留紀錄，不是留在腦袋裡。

    起源：第 14 話

  • 跨 agent 討論要收斂成文件

    兩個 agent 吵完的結論如果只留在對話裡，下次就要重吵一次。討論結果落成 repo 檔案，兩邊都讀同一份。

    起源：第 11 話 · 案例 →

Knowledge / Evaluation

重複教同一件事，問題不在 token。

  • 知識要落成檔案，不能靠記憶

    同樣的錯誤、同樣的規則、同樣的經驗，每天重新教一次。我一開始以為是指令太長，後來以為是上下文太肥。真正的問題是它每次都在重新學同一件事——所以重複出現的知識要寫成 repo 裡的檔案。

    起源：第 03 話 · 第 12 話

  • 做錯不只修結果，要留下經驗

    修好這一次沒有用，下次還會犯。所以每次修正都要問：這件事要不要變成一條規則、一份產品知識、還是一個測試？

    起源：第 03 話 · 第 09 話

  • 隱性知識要被挖出來

    我腦袋裡有一堆「這個欄位其實會影響那個排程」之類的東西，從來沒寫下來過。AI 不知道，所以它會做出技術上正確、業務上錯的判斷。這部分是靠它問、我答，然後把答案寫進 repo。

    起源：第 09 話

Evaluation · 進行中

  • 用自己的工具測自己的東西

    目前的驗證方式很土：把這套 workflow 用在真實的票上，看它會不會出錯，出錯就補規則。這不是一套嚴謹的評估方法，但至少是真實負載。

    起源：第 15 話

  • 還沒做到的部分

    我還沒有一套能回答「這次改善讓它變好多少」的量化方式。目前只能說某類錯誤不再出現，不能說整體品質提升了幾個百分點。這頁不會假裝已經有。
